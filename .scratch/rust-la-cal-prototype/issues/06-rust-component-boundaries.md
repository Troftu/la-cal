## Question

Choose the runtime, WebSocket, Zenoh, and OMS JSON validation dependencies after checking their actual capabilities and versions. The [encoding decision](04-schema-protobuf-mapping.md#answer) selects prost/prost-build; settle their versions, compiler pinning, and build integration here. Verify validation tooling covers the selected UCI 002.5.0 message dependency closure. Decide reusable client versus example executable responsibilities, server configuration, error surfaces, and ownership of connection/subscription lifetimes. Resolve how dependency and code-generation versions are pinned. Keep this an implementation-ready design, not an implementation ticket.

## Context

Use [Choose a client-focused relayed STOP demonstration](11-client-focused-stop-demo.md#answer) as the current component/demo contract. Each application owns its lifecycle logic, reporting, message processing, cleanup, and client connection directly. Earlier comments selecting runtime ownership, supervisor/health/control handles, and init/execute/shutdown hooks are historical. Preserve one OWP connection per Service, typed send(message), versioned generated bindings inside la-cal-client, and the chosen native tooling/validation/adaptation direction.

Settle client/subscription lifetimes, shared handles, typed receive delivery, reply matching, concurrent publications/operation acknowledgments, errors, and explicit closure using the relayed STOP flow. Reception must remain live while the orchestrator waits downstream; the client does not execute application handlers or automatically format lifecycle replies. Harness setup, process-exit observation, cleanup, STOP failure policy, and bounded shutdown remain application/evidence details, not reasons to recreate a runtime abstraction.

Selected receive model: subscribing returns a persistent typed subscription stream, consumed by application-owned async loops/tasks. Connection I/O and OWP acknowledgment processing remain independent of stream consumption and application handling. Independent registration ownership is settled below; the approved public signatures and behavioral error categories are consolidated in the Answer. Individual error-variant spelling is an implementation detail.

Selected subscription registration ownership: each subscribe call creates one independent OWP subscription ID and typed stream, even when another stream subscribes to the same message type. Each stream receives matching messages independently; closing/dropping one affects only its own registration and local delivery. Do not share a single wire registration through client-side reference counting/fan-out for this slice.

First-slice subscription scope: ordinary subscriptions only; defer the client-facing optional group argument and grouped demo usage. The user did not select subscribe_with/group options. This scope choice does not withdraw the separately recorded server-side OWP group requirements.

Client receive-buffer/backpressure design is out of scope for this first slice. The user delegated incidental handling to a simple implementation (logging is acceptable) rather than selecting configurable bounded queues, an Overflow error, or subscription termination on overflow. Do not treat those rejected recommendations as requirements or create a new buffering-design blocker. No receive-loss guarantee is established by this scoping choice.

Selected connection ownership: one application-owned OWP connection per Service, exposed through a single cloneable Client rather than separate public Connection-owner and messaging-handle types. Application code designates who performs teardown; explicit close through any clone closes the shared connection, and remaining handles/subscriptions observe closure. Dropping an ordinary clone does not close the connection. Application-owned teardown does not require a separate owner type. Exact signatures, last-handle/subscription drop mechanics, and internal type names remain implementation/interface details.

Selected subscription cleanup: provide explicit asynchronous close that unsubscribes and awaits operation completion, allowing the caller to observe failure. Dropping the stream stops local delivery and requests best-effort unsubscribe through background I/O; it cannot promise acknowledged cleanup. Closing one subscription leaves the connection and other subscriptions active. Cancellation, buffered-message disposition, and exact close signature remain interface details.

Selected stream item/error convention: Stream<Item = Result<T, ReceiveError>>. Polling yields Some(Ok(message)) for decoded messages, Some(Err(error)) for identifiable receive failure, and None once the subscription ends. A message-specific typed decoding failure yields a nonterminal error item; keep the subscription active for subsequent valid messages. Application code chooses whether to log or fail its operation. Unexpected connection loss produces a visible terminal error before end-of-stream. Concrete error names remain illustrative; malformed OWP framing/control behavior must be treated separately from a payload decoding failure. Elaborate buffering policy is excluded above.

Selected response matching: application code owns matching against its already-installed typed streams; do not add client-side waiters for this first slice. The orchestrator reads command status and ServiceStatus concurrently, matches downstream CommandID B and commandee processor identity, and separately matches commandee INOPERABLE by Service identity. It records both observations, accepting either arrival order, then sends its own response for upstream A. The illustrative tokio::select! example demonstrates this control flow, not finalized generated field names, stream error types, helper constructors, or deadline/reporting plumbing.

Selected type-to-wire mapping: generate message-root metadata alongside the versioned bindings for ServiceLifecycleCommand, ServiceLifecycleCommandStatus, and ServiceStatus. Typed send and subscribe infer the message-type topic and corresponding OMS JSON root encoding/decoding from the binding, rather than requiring callers to repeat topic/root strings. Applications still supply message content, identities, correlation, and domain state. Exact generated trait/metadata representation remains an implementation/interface detail; no raw-message escape-hatch API was selected.

Reconfirmed transport scope: no client TLS for now. Use the existing native loopback ws deployment; do not add a TLS backend, wss support, certificate/trust configuration, or TLS acceptance requirement to this first slice. Retain the documented TLS-capability exception rather than claiming complete WebSocket conformance.

Selected send completion: typed send(message).await waits for successful OWP publication completion (+OK), or returns the attributable operation/connection error. It does not mean subscriber receipt, command execution, or lifecycle completion. Use verbose OWP operation acknowledgment mode so positive completion can be observed; keep independent message dispatch active while awaiting acknowledgment. An acknowledgment timeout/disconnect after a write leaves the publication outcome uncertain, not proof of nonpublication; no automatic retry is added. Allow concurrent application calls but internally serialize acknowledgment-tracked PUB/SUB/UNSUB operations: only one operation awaits its response at a time. This selected correlation approach avoids relying on a pipelining/FIFO response guarantee because OWP responses lack operation IDs.

Selected caller-cancellation behavior after transmission: background I/O retains ownership of a sent acknowledgment-tracked operation even if the caller drops its pending future or an application timeout stops waiting. Consume that operation's response before advancing the serialized queue; caller cancellation does not undo publication, retry it, or close the shared connection by itself. Incoming-message dispatch remains live and the configured operation deadline still applies.

Selected acknowledgment-timeout behavior: expiration of a sent operation's acknowledgment deadline fails the connection. Stop admitting/sending further operations, fail pending callers visibly, notify subscriptions with their terminal connection-failure error, and close the transport with bounded cleanup. Do not proceed to the next queued operation or retain a receive-only connection: a late uncorrelated response could otherwise be misattributed. A sent publication's outcome remains uncertain, while queued unsent operations fail without being transmitted. No automatic retry or recovery is added.

Selected demo process ownership: demo-driver launches and owns the local Zenoh router, la-cal server, orchestrator, and commandee-service processes. It waits for communications/application readiness, initiates and observes the STOP exchange, separately observes commandee process exit, and cleans up the remaining processes. The harness owns the overall verdict; orchestrator does not launch or own commandee. A separate shell-owned process/exit-verdict layer is not selected. Exact command-line spelling, executable discovery, and bounded child cleanup remain interface/evidence details.

Selected tooling version direction: use the latest stable releases of the selected tools/dependencies, rather than freezing the older host-tested baseline. The 2026-10-04 lookup identifies Rust 1.99.0, Tokio 1.53.2, tokio-tungstenite 0.30.0, Zenoh 1.10.1, prost/prost-build 0.14.4, futures-util 0.3.34, and upstream protoc 36.2. Recheck releases when establishing the implementation baseline, retain the resulting workspace Cargo.lock, and record actual tool/generator versions and the dependency graph. Use locked builds/checks against that recorded dependency snapshot. This changes tooling selection, not the pinned OMS/UCI standards profile. The complete latest-stable graph has not been built on Rust 1.99.0.

Selected compiler sourcing: use the latest stable upstream protoc on PATH for prost-build generation. It is a build-time dependency, not an application runtime dependency. No custom executable path or older compiler-version pin is required for this slice; record the actual compiler version in generation/build evidence. The separately maintained protoc-bin-vendored helper is not selected because its latest 3.2.0 package bundles protoc 31.1, behind upstream 36.2 at lookup time. Current prost-build does not itself bundle protoc.

Selected router readiness/outage observation: la-cal's Zenoh adapter uses stable router-ZID snapshot APIs with bounded startup polling before admitting OWP clients and periodic connectivity checks afterward. A subsequently observed router loss latches run failure; fail visibly and close client connections with bounded cleanup, even if the SDK reconnects. A disconnect/reconnect between snapshots may be missed, and five-second required-event deadlines do not imply five-second transport-loss detection. Do not enable unstable transport/link listeners for this slice. demo-driver owns the router process and the overall verdict/cleanup, but adapter-side connectivity observation remains la-cal's responsibility. Poll interval and related low-level settings are simple implementation details; do not claim every transient outage is observed.

Selected adapter execution seam: expose an ordinary async publication method, illustratively adapter.publish(topic, json_bytes).await, with synchronous validation/encoding/Zenoh publication offloaded internally and operation-deadline handling owned by the adapter. Server connection I/O remains independent; callers do not manage blocking worker handles or timeout plumbing. Return success only after the selected publication-completion milestone, and send OWP +OK only on that success. Surface failures visibly without automatic retries. Deadline expiration cannot forcibly cancel already-started blocking work and does not prove nonpublication; bounded run/cleanup failure must not depend on indefinitely joining such work. Exact helper types and signatures remain illustrative.

Selected relay failure policy: downstream STOP rejection/failure or expiry of the required downstream result/INOPERABLE observation produces the orchestrator's own upstream terminal REJECTED/FAIL response for CommandID A when its connection remains usable, including when downstream B was already issued. User chose this over the research recommendation of ACCEPTED/FAIL for an attempted relay; the schema permits either combination. Preserve upstream context and processor identity; do not rewrite/forward the child's reply or fabricate success. The project's rejection classification reports that the relay's success conditions were not met; it must not imply B was never sent, STOP never executed, or commandee reached an inferred state. Send one terminal response after the failed milestone/deadline, not an early ACCEPTED followed by failure. If upstream publication/connection is unavailable, report the cause visibly and let driver-observed failure/deadlines establish the failed verdict. No retries or recovery; demo-driver owns cleanup. Optional diagnostic data uses CommandProcessingStateReason with a required valid Reason and optional truthful Description/AssociatedID; omit AssociatedID in the minimal sender rather than relying on the unrepaired polymorphic codec.

Selected independent-assessment interpretation: use documented strict OMS JSON checks plus an XML reconstruction for independent XSD verification, expanding repeating JSON arrays into schema-ordered sibling XML elements and using xsi:type to assess $type-derived values. The official array/$type wire rules remain unchanged. Document how this intended-encoding assessment interprets the ambiguous array-recursion/empty-attributes wording in Rev B Table 6.1-2; do not claim the XML bridge is explicitly specified by that table or establishes exact literal infoset equivalence. The user selected this approach rather than requiring authoritative clarification first.

Selected validation simplicity/fallback boundary: production keeps the SLEET-style direct Rust validator, with scoped repairs and the research note's verification gates. Independent XSD assessment stays in development/tests, not the normal runtime message path. Do not add a production XML/libxml2 assessor or pre-authorize a native fallback for this slice. If the scoped repairs cannot meet the verification gate, stop and revisit the production engine decision rather than retaining a known validation gap or silently adding a second engine. The original selected encoding/validation boundaries and client-no-runtime-schema-validation choice remain intact.

Selected generated-artifact workflow: generate the selected UCI bindings explicitly and check the generated Rust into the repository, with schema/generator provenance and reproducibility verification. Ordinary builds compile those bindings without running the Python UCI generator. Also check in the project-defined envelope .proto source carrying OMS JSON bytes; it is not generated from XSD. prost-build generates the envelope Rust during Cargo builds using latest stable upstream protoc on PATH. Schema-derived typed UCI proto generation remains deferred; the user clarified the earlier proto request and reaffirmed bytes-only transport.

Selected connection readiness: connect(config).await returns only after successful WebSocket/OWP establishment, INIT/INFO completion, and selected-profile checks. On success, callers may immediately subscribe/publish; setup failures are returned by connect within the configured connection deadline. No separate start_connecting()/ready() public flow is required for this slice. Communications readiness does not imply application NORMAL.

Selected explicit connection closure: bounded graceful close. Stop accepting new operations from all shared handles; finish already-admitted operations within the configured deadline, perform WebSocket closure, and finish background I/O. If draining fails or exceeds its deadline, report failure and proceed with bounded cleanup rather than waiting indefinitely or retrying. Final publication calls are awaited before application teardown invokes close. Concrete method/error names and cancellation/drop details remain interface/implementation details; no immediate-cancel close mode was selected.

`la-cal` and `orchestrator` are native. WASIp3 capability of other Service applications and `la-cal-client` remains a follow-up direction, but portability choices and a Wasm acceptance requirement are deferred to [Spike WASIp3 support for Service lifecycle and LA-CAL clients](../../wasip3-service-portability/issues/01-wasip3-service-runtime-spike.md). Re-scope its old runtime assumptions before execution; it does not block this native interface decision.

The [ASB routing decision](05-zenoh-asb-contract.md#answer) retains one Zenoh session, a startup subscriber on `la-cal/uci/002.5.0/*`, exact message-type publication keys, local connection-owned OWP subscription registration, and a bounded outbound queue per connection. The approved defaults are 64 outbound messages per server connection and 100 ms stable router polling, with the settled offload/deadline and resource-ownership behavior. SDK-managed reconnect attempts are acceptable, but detected loss still fails the run; no application recovery is required. Actual adapter traversal is required; SDK-local delivery is accepted and physical-router-hop evidence/multiple CAL Servers remain deferred.

### Components and dependency direction

- **la-cal-client:** reusable native Tokio OWP client, generated versioned UCI messages/metadata, typed JSON encoding/decoding and independent subscription delivery. No Service supervisor, application handlers, automatic lifecycle replies, client-side reply waiters, or runtime schema assessor.
- **la-cal:** project-owned adaptation of SLEET's OWP frontend/local subscription-group routing, direct Rust OMS JSON validator and Zenoh/Protobuf adapter. It owns the shared session/startup subscriber, OWP registrations, server queues and connectivity/failure observation.
- **orchestrator / commandee-service:** applications depend on la-cal-client, each own one shared connection, lifecycle state/reporting and application processing. They implement the selected relay/STOP behavior directly.
- **demo-driver:** uses la-cal-client as commander/observer and Tokio process facilities as the harness. It launches/owns router, server and applications, installs observation before application reports/commands, verifies message/state/exit milestones, and owns bounded cleanup/verdict. It does not make orchestrator the process owner of commandee.
- Mechanical package-internal organization and shared helper placement are implementation details. Preserve these responsibility boundaries rather than introducing a generic lifecycle execution framework.

### Approved public client surface

Signature declarations below define the selected surface, not compiled implementation code:

```rust
impl Client {
    async fn connect(config: ClientConfig) -> Result<Self, ClientError>;
    async fn send<T: Message>(&self, message: &T) -> Result<(), ClientError>;
    async fn subscribe<T: Message>(&self) -> Result<Subscription<T>, ClientError>;
    async fn close(&self) -> Result<(), ClientError>;
}

impl<T: Message> Subscription<T> {
    async fn close(self) -> Result<(), ClientError>;
}
```

Client is cloneable; all clones share the same OWP connection. Explicit close through any clone closes it for all handles/subscriptions. Dropping an ordinary clone does not close it. Application code owns reliable teardown; last-owner/drop mechanics use best-effort resource cleanup rather than promising acknowledged asynchronous close.

ClientConfig supplies the server endpoint, OWP participant identity and configurable required-operation deadlines; fixed supported profile/root mapping and verbose acknowledgments come from the selected implementation profile. Configuration spelling/builders and internal helper names are delegated. connect awaits successful WebSocket/OWP INIT/INFO and profile checks before returning usable communication.

Generated Message support applies to the three global roots and supplies root/topic/profile encoding and decoding, not arbitrary internal XSD types. Bindings live in a versioned messages module within la-cal-client, with the three application-facing root types. Exact metadata representation, supporting trait bounds and private helper names are mechanical details, not additional public raw-message APIs.

Subscription<T> implements Stream<Item = Result<T, ReceiveError>>. Each subscribe creates its own OWP registration, including repeated subscriptions to the same type. Explicit stream close consumes it, awaits unsubscribe completion and affects no other stream. Drop stops local delivery and requests best-effort unsubscribe. Message-specific decoding failure is a nonterminal error item; unexpected connection failure is a visible terminal error before end-of-stream. Client buffering mechanics remain delegated under the explicitly scoped first-slice policy; no loss guarantee or configurable overflow API is introduced.

### Operation attribution, cancellation and closure

Concurrent application calls are supported, but only one acknowledgment-tracked PUB/SUB/UNSUB is in flight per connection. Dispatch incoming MSG and process WebSocket controls independently while awaiting its response. send completes on positive OWP publication acknowledgment, not subscriber receipt or lifecycle completion.

After transmission, background I/O owns the operation despite caller cancellation. Consume its response before sending the next queued operation. If its acknowledgment deadline expires, fail the shared connection, stop sending queued operations, fail pending callers, terminate subscriptions visibly and perform bounded cleanup. A transmitted publication may have occurred; queued unsent operations were not published. Do not retry or misattribute a late response.

ClientError/ReceiveError distinguish configuration/connection/negotiation failure, local encode/decode failure, attributable OWP rejection, deadline/transport/protocol failure and closed-connection use as appropriate. Preserve server error details and sent-versus-unsent/uncertain publication facts. Exact variant spelling is delegated; malformed protocol/control input is not downgraded to one message's recoverable decoding error.

Graceful connection close stops new admissions, drains already-admitted operations within the deadline, closes WebSocket and finishes background I/O. Return visible failure and proceed to bounded cleanup if draining/closure fails; never wait indefinitely or retry. Await final publications before invoking close. Subscription/connection drop cleanup does not claim the guarantees of explicitly awaited close.

### Server/adapter interfaces and configuration

Server-side call sites use an ordinary async publication seam, illustratively adapter.publish(topic, json_bytes).await. It internally offloads synchronous validation/encoding/Zenoh publication and owns operation deadlines. A success result permits OWP +OK only after the selected validated-publication milestone. Receive/decode/validation/fan-out follows the actual subscriber path without republishing or direct local echo. Keep accepted JSON bytes unchanged regardless of parsed assessment representations.

The server opens one explicit local-router session and the fixed startup wildcard subscriber before admitting clients. Use bounded stable router-ZID polling for readiness and periodic snapshots afterward. Observed loss permanently fails the run and closes client connections; SDK reconnect cannot resume it. Between-poll outages may be missed and transport-detection latency is not guaranteed by event deadlines.

Started blocking publication/validation work cannot be forcibly canceled. Failure/timeout remains visible and may have an uncertain publication outcome. Server/harness cleanup must not depend on indefinitely joining such work; driver-owned bounded process termination/reaping supplies the final escape from stalled child cleanup.

OWP service/topic authorization, group delivery/registration cleanup and validation behavior follow the selected standards/SLEET-adaptation repair plan. Client demo subscriptions omit groups, while the server retains required group behavior.
