# SLEET server reuse with the selected Zenoh/Protobuf ASB

Date: 2026-10-03. Research for [Assess reusing SLEET's LA-CAL server with a Zenoh/Protobuf ASB](../issues/10-sleet-server-reuse-feasibility.md); recommendation, not an adoption decision.
**Verdict: feasible and probably the smallest OWP implementation path, through project-owned source adaptation. The unchanged binary and an unchanged server crate dependency cannot implement this ASB contract.** Retain the OWP frontend and local subscription/group registry; separate ASB publication from local delivery and add a supervised Zenoh/Protobuf adapter. Validation fidelity and failure/cleanup behavior are substantial remaining work, rather than reasons to rewrite the OWP grammar.

## What can actually be reused?

| Option | Source-grounded assessment |
| --- | --- |
| Run unchanged SLEET binary | No Zenoh session, Protobuf envelope, bus receive ingress, or transport injection in startup; it constructs `Router::new()` and passes it to `server::run` ([main.rs:426–452][startup]). Configuration only selects identities/schema/topics/listeners, not middleware. |
| Depend on unchanged `sleet` as a library | No `sleet/src/lib.rs`, no `[lib]` target, and `main.rs:8–15` declares private modules ([main.rs][main]). `pub` functions inside these modules are not exported to downstream crates. `server::run` accepts the concrete `Arc<Router>`, not an adapter. Merely adding a Git/path dependency does not expose the server. |
| External OWP↔Zenoh bridge around unchanged binary | Does not remove its direct local PUB fan-out, cannot gate its `+OK` on Zenoh completion, and risks circulating received samples through PUB. Cannot meet the no-direct-echo/error/readiness contract. |
| Project-owned adaptation/fork | Recommended candidate: retain `server.rs`, `router.rs`, OWP types/tests and configuration logic; replace publication transport, add validated bus ingress, repair contract mismatches. Keep provenance and a reviewable upstream delta. |
| Selectively reuse parser/types and rewrite server | Technically viable; loses ready-made negotiation/error/authorization/group/cleanup code and corresponding tests. Justified if validation or task-ownership decisions make the existing frontend too costly to maintain, not required by Zenoh itself. |

**Library extraction is optional for a standalone adapted `la-cal` executable, necessary if another crate must call the reused server directly.** In the latter case add a project-owned `lib.rs` with one small server-running/configuration interface and keep registry/schema/adapter internals private. A public transport trait is not an upstream capability. An internal injected publisher interface plus test adapter is sufficient; generic/static dispatch, boxed futures, or a concrete channel handle can satisfy it without choosing an async-trait dependency now. Keep the module deep: callers learn startup/run/shutdown and error semantics, rather than all the internal SLEET arguments.

## Publication ordering: the exact seam to change

Current `server.rs::process_pub(topic: String, raw_json: String, service: Arc<ServiceConfig>, schema: Arc<Schema>, router: &Router) -> Result<(), (OwpError,String)>` does:
1. Check allowed topic; disallowed → Illegal-State (`663–671`).
2. `spawn_blocking`: parse JSON, check a binding for a known global root, then `validate_oms_json` (`673–712`). Binding mismatch currently → **Illegal-State**, unlike the project's selected **Invalid-Message** payload-policy error.
3. Retain the original `raw_json` alongside extracted message name (`700–727`), then directly call **`router.publish(...)`** (`729–732`). This local-delivery function returns `()`; full/closed recipient queues cannot fail publication.
4. Return success; `handle_active:570–574` sends verbose `+OK` **after local enqueue attempts**, with no bus acknowledgment. The publisher's own queued MSG is polled only after this handler returns; other connections run independently.

All four steps are source evidence ([server.rs:653–737][pub]), not actual Zenoh proof. Replace **step 3**, retain protocol parsing/authorization and successful-operation acknowledgment dispatch, and share payload validation with new bus ingress. Do not just replace `Router::publish` with a function that both puts and fans out: it must become a clearly receive-only delivery method.

### Recommended narrow interface and topology

```text
one la-cal process:
  OWP accept/connection tasks ── validated publication ── ASB publisher adapter
    │ local SUB/UNSUB                                 │ envelope encode, Zenoh put
    ▼                                                 ▼
  local registry/group selector ◀── validated receive ◀── one Zenoh startup subscriber
    │ original JSON + connection/SID                   envelope decode + JSON validation
    ▼
  bounded per-connection MSG queue ── WebSocket owner
  server supervisor owns adapter session/listener/tasks and OWP shutdown
```

- Inject a small **internal publication interface** at `process_pub`: accept a closed-set route/message identity and validated original JSON bytes; complete with success only after the actual Zenoh publication operation succeeds, or return an infrastructure error. The interface promises no fan-out, receipt, replay, or lifecycle result. Test adapters can delay/fail completion; a channel-backed adapter must await its operation result, not acknowledge queue admission.
- Keep `Router::{subscribe,unsubscribe,remove_connection}` local. Rename/split its current `publish` to `deliver_received` accepting only a validated receive value. Make validated publication/receive constructors private to their respective paths, so bus ingress has no ordinary route back to publisher. No extra envelope provenance field is needed.
- Open **one Zenoh session**, explicit loopback router endpoint, discovery disabled; declare **one** lifetime subscriber `la-cal/uci/002.5.0/*` before accepting OWP clients. Publish only exact `la-cal/uci/002.5.0/{ServiceLifecycleCommand,ServiceLifecycleCommandStatus,ServiceStatus}` keys. OWP topics are those three message names. SUB/UNSUB never declare/undeclare Zenoh resources.
- Encode project proto3 `OmsJsonEnvelope { bytes oms_json = 1; }` using the selected prost/prost-build direction. Put the original validated UTF-8 JSON bytes, excluding OWP framing. On receive, reject non-Put samples, unsupported/non-exact keys, malformed Protobuf, empty bytes, invalid UTF-8/JSON/schema, unsupported root, and key/root mismatch; report/discard, then continue listening. Unknown envelope fields follow ordinary decoder behavior and do not bypass payload checks.
- Local publisher delivery must come **from the Zenoh subscriber** through decode/validation. Allow session-local origin/destination: [Zenoh Locality 1.10.1][locality] expressly supports it. Do not discard own-origin samples or JSON whose Service ID equals the publisher: those are legitimate self-subscription deliveries. No duplicate cache or forced router hop is required.
- Never republish received samples. Distinguish path provenance in types/control flow, not by a forged or overloaded sender ID. Forwarding to multiple SIDs is fan-out, not a transport loop. Remote publishers receive no fabricated OWP `-ERR` on an unrelated local client when their sample is invalid.
- **PUB `+OK`: validation + completed put operation; SUB `+OK`: installed local entry against already-active receive path; UNSUB `+OK`: removed local entry.** Only verbose connections receive successful-operation `+OK`; both modes receive errors. Put success is not recipient receipt, router receipt, START acceptance or command completion. The client must tolerate asynchronous MSG/status interleaving.

The adapter is a deep module: it hides mapping, envelope operations, receive validation and session ownership behind publication completion, validated reception, readiness/failure observation, and shutdown. There is no reason to make every SUB a middleware operation or to reproduce OWP inside Zenoh.

## Local groups, queues, and cleanup

- [router.rs:48–160][registry] indexes by `(connection_id,SID)`, ordinary topic→message subscriptions, and topic→message→group members. It installs under a write lock; the same SID on different connections is independent. Limits are currently 2048 subscriptions/connection, independent of the 1024 MSG queue capacity.
- [router.rs:197–256][fanout] gathers matching ordinary subscriptions and selects one member of each matching group under a read lock, then enqueues outside the lock. Group member keys are ordered, with atomic round-robin counter. This already filters by message before selection and scopes group identity by topic. Round-robin is a reusable policy, not mandated by LA-CAL §4.8/CERT LACAL-000009. No publisher exclusion exists.
- [router.rs:163–195,258–347][registry] removes SID/connection indexes and prunes empty direct/group buckets. This logic can remain substantially intact. One shared server means group selection happens once per received bus sample; it would not establish distributed group coordination across multiple servers, which is deferred.
- **Necessary policy change:** [deliver_or_drop:349–381][drop] uses `try_send` but merely debug-logs/counts Full/Closed. Contract requires visible Full → **close the entire slow OWP connection and dispose all its SIDs**, while healthy recipients continue. Add connection-owned cancellation/failure notification to delivery targets/subscriptions; observe it in the WebSocket owner. Removing only one SID or dropping only that MSG is insufficient. Skip already-failed targets; keep group selection to at most one eligible member, without inventing reliable re-delivery after overflow.
- **UNSUB race to cover/fix:** target snapshots and already-queued `ServerOp::Msg` survive registry removal, and the writer checks no active SID before sending ([fanout][fanout], [server.rs:320–337][io]). SID reuse can attribute an old queued message to a new subscription. Carry a registration generation/liveness token with queued delivery and discard stale entries in the writer, serialized with SUB/UNSUB completion. Existing quiet-queue UNSUB tests do not prove this race safe.
- **Forced-abort cleanup:** `handle_connection` cleanup occurs after awaiting `connection_loop`; `run` aborts remaining tasks on drain expiry ([server.rs:133–154,243–260][sv]). Abort/panic bypasses that post-await cleanup. Keep connection IDs in supervisor-owned task bookkeeping or an equivalent cleanup strategy so final task completion/abort removes registry entries and active-count ownership correctly. This matters more when the adapter retains the registry for server lifetime.
- Continue bounded WebSocket sends, but make queue capacity and required-operation waits configurable under the five-second-default contract rather than treating upstream hard-coded 10s INIT/upgrade and 5s writes as selected interfaces. Frame/write limits should be validated; upstream config accepts numbers without all Tungstenite invariants, and defaults permit very large buffers ([config.rs:503–529][cfg]).

## I/O, readiness, outage, and shutdown ownership

- Reusing the unsplit WebSocket owner is viable. Awaiting validation/put inside `handle_active` pauses that connection's read/MSG/control-frame polling. Keep blocking adapter execution off networking tasks and use a bounded pending-operation/completion arrangement if continuous I/O is needed; splitting into separate read/write tasks is **optional**, not inherently required by Zenoh. Serialize operation completions because OWP `+OK` has no request ID.
- Current loop handles Text, rejects Binary, explicitly echoes Ping payload in Pong, tracks Pong/activity, and sends Policy/Away Close on timeouts/shutdown ([server.rs:279–400][io]). On inbound Close it immediately breaks; after sending Close it also breaks. [Pinned Tungstenite docs][ws-doc] require driving/flushing queued automatic responses and the close handshake. Add bounded close-handshake progression and control-frame tests; neither the current source nor a disconnect-only assertion proves RFC closing behavior.
- **Execution trap:** Zenoh 1.10.1 [PublicationBuilder `IntoFuture`][zenoh-put] calls synchronous `wait()` before producing `Ready`. `timeout(put(...).await)` is not proof of a hard runtime limit. Keep synchronous work in bounded adapter workers or otherwise verified execution mechanics; a timed-out started blocking job can still finish. Never retry it or send late `+OK` after the run has failed.
- **Receive trap:** [DefaultHandler][zenoh-handler] wraps [FifoChannel][zenoh-fifo]; its callback uses blocking `sender.send` on a bounded channel. A slow receiving task can block a Zenoh thread, including session-local publication. Prefer a small synchronous callback that nonblockingly transfers owned samples into a bounded ingress queue; decode/validate/deliver in a supervised task. Report ingress overflow/worker failure and fail visibly rather than silently losing required demo evidence. Exact capacity/execution policy remains for [Choose the Rust component interfaces and dependencies](../issues/06-rust-component-boundaries.md).
- Startup owner must establish configured router connectivity **and** the wildcard listener, then start OWP accepting and readiness. Current `ready` is only a bind flag and `/health` always returns 200 ([server.rs:60–64][sv], [admin.rs:113–147][admin]); `/health` cannot establish ASB readiness. Startup failures/timeouts return failure and release any partial resources.
- [Session API][session] distinguishes `is_closed`/explicit close from connected-router availability. [Pinned `api/info.rs`][zenoh-info] exposes stable `routers_zid`; transport/link event listeners require the unstable feature. Stable polling is a candidate for **detected** loss, can miss a disconnect/reconnect between polls, and must not be advertised as exhaustive transient-outage evidence. Event-based observation or supervisor router-process exit observation needs a concrete decision/verification if selected.
- [Pinned DEFAULT_CONFIG][zenoh-config] supplies mode/connect/listen/scouting/open-return settings and a default transport lease of 10000ms. An explicit client-mode loopback-router configuration is a narrow topology recommendation; generic `open` success, subscriber declaration, `put` success, and SDK-local MSG activity individually do not prove the router remains connected. Five-second event waits do not automatically impose five-second transport-loss detection.
- Known put/worker/session failures produce `Internal-Error` or connection failure, never success. Detected router loss latches run failure, clears readiness, stops acceptance, cancels OWP connections and adapter tasks, and triggers demo cleanup even if SDK reconnects. Invalid inbound data is report/discard, distinct from fatal infrastructure loss. OWP connection state, ASB state and Service lifecycle state remain separate.
- `la-cal` process supervisor owns the session/listener and receive/publish/health tasks; per-connection shutdown does not close the shared session. Orderly server teardown stops acceptance/new work, signals OWP close, removes all registrations, stops/joins ingress/publication/health work within defined bounds, undeclares the subscriber and explicitly closes the session. [Session::close][session] stops entities and makes later publication fail; dropping one clone is insufficient. Resource cleanup also runs for bind failure, adapter startup failure and forced connection abort. SLEET's existing `run_until_shutdown` supervises only server/admin tasks ([main.rs:303–345][main]).

## Validation and generated-client integration

- The custom schema module reads includes, sequences/choices, extension inheritance, simple restrictions and selected facets ([parser.rs:54–61,259–327][parser], [model.rs:49–140][model]); validator checks one global root, shape/members, occurrences, choices, `$type` derivation, primitive categories, integer ranges and compiled facets ([validator.rs:63–94,131–455,484–647][validator]). These are valuable implementation and regression inputs, not complete XML Schema assessment.
- **Confirmed selected-root gaps:** `DateTimeType` Main XSD **117038–117045** combines xs:dateTime with `.+Z`; `DurationType` **117745–117750** derives from xs:duration. Validator `builtin_value_kind:572` treats other `xs:*` as strings, so temporal lexical/calendar validity is not fully assessed. A string ending `Z` can satisfy the custom pattern without being a dateTime; TimeUp requires a real duration. SecurityMarkings **8565–8585** uses `whiteSpace=collapse`, absent from `Facet`/parser. Correct validation must normalize for assessment without changing forwarded bytes.
- Namespace handling uses local-name schema maps and strips non-XSD prefixes ([parser.rs:713–723][parser-names], [validator.rs:79–89][validator]), unlike LA-CAL §6.1.1/§6.1.5.2 namespace identity. The selected same-namespace 2.5 schemas reduce the immediate surface, not a full extension conformance claim. Unsupported constructs/pattern failures are skipped or warned, not fail-closed ([facets.rs:61–173][facets], [model.rs:397–423][model]). General nested particles/choice cardinality are not represented fully.
- Numeric bound/facet assessment uses f64 ([facets.rs:35–47,267–348][facets]); the executed static three-root closure has boolean/dateTime/duration/string/unsignedInt leaves, **no float/decimal leaves**. Do not imply every general SLEET limitation breaks minimal START. Derived optional branches, unrestricted integer/decimal lexical interpretation, and duplicate JSON-member handling still need independent negative/edge-case coverage appropriate to the supported closure.
- Shared validator interface should return validated message/root identity while retaining original bytes for both OWP PUB and bus receive. Either repair direct validation for the selected dependency closure with independent XSD-backed evidence, or replace it behind this seam. XML-backed alternatives require a faithful OMS JSON mapping, including arrays, inheritance order, namespace/primitive rules and `$type`; the questions in [json-validation-options.md](json-validation-options.md#oms-json-mapping-constraints) remain unresolved. Reuse does not force adoption of SLEET's validator.
- Current `process_pub` validates outbound only; `Router::publish` assumes its input is valid. A bus receive task must perform full independent inbound checks and global supported-topic/root policy, rather than use any one local publisher's `ServiceConfig`. Enforce the three-message deployment policy even when the complete XSD is loaded, and turn configured supported-root/type mismatches into the selected Invalid-Message behavior. SUB pairing remains a local authorization/registration check.
- **Client cannot be adopted unchanged:** [CalClient:100–283][client] owns one stream and requires `&mut self` for every operation/recv; no shared handles, supervisor, explicit shutdown, operation deadlines or background reception. `expect_status:268–277` consumes a MSG and returns UnexpectedServerOp instead of preserving it while awaiting `+OK`. A simple mutex around it can make a blocking recv prevent send/report/control progress.
- Keep selected `la-cal-client` typed `send(Rust message)` with one connection actor/IO owner, serialized pending OWP operation status, independent MSG dispatch, shared handles and explicit owner shutdown. SLEET's parser/handshake/error ideas remain useful. Preserve INFO metadata (current client discards it) and validate negotiated subprotocol/version as appropriate. The lifecycle runtime owns Service connection/supervisor; driver owns its own; one pending application action is separate from OWP-operation serialization. Hook interface remains pending.
- Generator [TARGET_MESSAGES:21–36][gen] omits both lifecycle-command roots; [discover_type_closure:884–949][gen-closure] already accepts chosen roots internally, but CLI lacks a roots selector. [RustGenerator:343–394][gen-render] emits the single-member `UciMessage` wrapper; arbitrary `Serialize` structs alone do not supply it, and no route/profile metadata trait is generated. Project adaptation must select three roots, add/associate root/topic/profile metadata, retain complete required dependencies, and verify encoding independently of Serde derives.
- Executed in-memory discovery/render succeeded for these three roots: **26 complex + 33 simple types, 24 enum simple types, 4 choice types, 0 unresolved named references**, rendered **242637 UTF-8 bytes**, with all three root variants. This proves Python discovery/rendering only. It emitted **no `$type`**; optional `CannotComplyType.AssociatedID` (Main **14278–14299**) can use derived ID types, so static named closure is not complete polymorphic support. [Previous conservative analysis](json-validation-options.md#pinned-schema-artifacts) found 341 types with derived closure; that count was not rerun here. Compile, optional/derived serialization/deserialization, and real schema validity remain necessary checks. Full-schema generation stays deferred.
